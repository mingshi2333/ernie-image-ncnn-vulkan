# RAM 可用量估计与缓存命中修复

2026-09-07，改进 Linux RAM 余量读取，并修正缓存命中时重复预留权重空间的问题。相同 512×512、映射加载、6 GiB 缓存的完整八步运行现在产生 **13 次缓存命中**；25 个张量、4,981,760 个有限元素和最终 PNG 与原生基线逐字节相同。此前组合运行的零命中失败继续保留。当前仍有 **54 次压力回收**，不能宣称缓存保留稳定或已取得正式性能优势。

## 实现

- 新增独立的 `src/host_memory.*`，将 Linux 内存读取从权重会话中拆出。每次重新读取主机 `MemAvailable`、当前进程的 cgroup-v2 路径和所有有限上级限额，避免进程迁移后使用旧路径。
- 原实现直接计算 `memory.max - memory.current`。由于后者包含文件缓存，这会把可回收的文件页也视作不可释放的占用。新实现只对干净、非活跃文件页估计回收余量；同时受 `inactive_file`、扣除 shmem 的文件总量和已用量约束，再扣除 dirty/writeback。匿名内存、锁定权重、活跃页、slab 和 swap 不获得额外回收额度。
- 对每个有限 cgroup，先后两次读取用量，取较大值减去上述回收估计，再计算限额内余量；最终仍受整机 `MemAvailable` 和所有上级限制约束。采用饱和运算，缺失或异常的可选文件统计按零回收处理，必需输入失效则停止缓存准入。这是余量估计，不能保证下一笔分配必然成功。
- 缓存命中只检查现有 RAM 预留量；加载尚未缓存的块还必须预留估计载荷。真实余量不足仍逐个释放空闲 Net，正在执行的租约不受影响。实际统计在请求末尾清理前读取，所以本例 54 次回收不包括最终析构。

计数器含义依据 [Linux cgroup-v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files)。实现没有修改内核限额或执行强制页缓存清理。默认 GPU/RAM 权重选择仍为 auto；映射和跨步 RAM 缓存继续默认关闭。

## 检查与完整执行

首次 CPU/Vulkan 相关检查共 16 项通过；明确文件列表和类型计数的关系后，对最终策略重新构建两种版本，针对内存读取、会话、真实 Vulkan GEMM 和已安装 C++ 消费者的 **10 项检查全部通过，无跳过**。两轮日志均保存，不把重复检查累计成不同功能的覆盖数。测试覆盖文件回收额度、真实匿名内存压力、上级限额、迁移、损坏输入、溢出、命中不重复预留及实际压力下回收。

完整模型输入和资源约束均沿用前次组合运行：15-token 原生 Vector 文本，source32/64 DiT 文本槽，保存初始 latent，512×512，8 步 Vulkan FP32，CPU direct VAE；源码隐藏、网络禁用、模型只读。运行前后验证 394 个源码、二进制、脚本、输入和基线绑定。

参数保持 `--dit-weights auto --gpu-reserve-mib 8192 --dit-cache-mib 6144 --ram-reserve-mib 3072 --model-loading mapped`。8192 MiB 用于主动选择 RAM 分支，并非实际耗尽 GPU 后恢复；本次 16 GiB cgroup、6 GiB 缓存、3 GiB RAM 预留均为可配置实验值。GPU 计算和推理数学保持原样。

## 保留限制

前次[映射加缓存运行](../runtime-model-loading/README.md)的零命中、12 次回收和原比较器失败保持原样。本次沿用至少一次命中的原要求并通过，但 13/288 的复用比例有限，回收次数和 cgroup max 事件均增加。它证明部分跨步复用与输出一致，尚未证明文件映射和准备权重缓存能稳定共存，也没有对两项修正分别作因果归因。

此次与历史 386.096 秒、其他缓存模式的单次耗时没有控制文件缓存状态，不能据此计算正式收益或优劣。下一步需要改善压力变化时反复准入和回收的问题，并以相同程序、固定输入和受控重复运行检验净收益；不得只以命中次数选择默认值。
