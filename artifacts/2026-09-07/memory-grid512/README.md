# 四种权重读取/缓存设置：16 次开发对照已完成

2026-09-07。预先冻结的四种配置各完成一次预热和三次测量，共 16 次独立进程生成。全部得到与基线逐字节相同的 512×512 PNG，全部进程成功结束，OOM/OOM-kill 为 0。这里只比较本项目同一个程序的设置，不是与参考项目的正式速度、内存或质量比较。

## 设计与身份

[冻结协议](../memory-grid-protocol/README.md)先于执行保存。源码为 `b6b80d32c19f0c31b97ab31b2010e32d0bf9c8af`，程序 SHA256 `ff2f934f317a602f3d098bf6d74cd7c2e2a6de725ed8fcf04d8d1e2bcbaa3e1c`，计划 SHA256 `04d0e4e7454436853e4031e1eee55d367cfb2a2edd33038c71eb7319081d8a1b`。本轮之后新增的紧凑读取缓冲和 Windows 路径改动不属于该程序。

全部配置使用相同 shared source32 包、15 个原生 token、64 个 DiT 文本槽、保存的初始噪声、8 步 Vulkan FP32、CPU Vector 文本和 direct VAE、PE 关闭、GPU0、2 个 CPU 线程。每次明确指定 RAM 权重。对比 stdio/mapped × 缓存 0/6144 MiB，RAM 预留 3072 MiB。每次在新进程执行，预热后按冻结的循环次序执行三轮测量，未丢弃或重跑任何样本。

原有保护设置为进程组内存 16 GiB、交换配额 0、主机可用 RAM 至少 3 GiB、整卡显存采样不超过 6144 MiB，阶段超时 1800 秒。它们是本项目的实验设置，不是硬件最低要求。源码和程序采用独立只读快照，原仓库在运行中隐藏，网络关闭。测量关闭张量 trace 和分配插桩。每轮都先验证所有模型文件，页缓存会被预热，但没有进行冷缓存或稳定缓存控制；另有独立 CPU 核心运行编译/Wine 检查，因此没有完全控制背景负载。

按照冻结方案逐轮配对并取耗时比的中位数，mapped/缓存关闭相对 stdio/缓存关闭观测到约 **20.85%** 的耗时下降；stdio 中开启缓存约 **6.10%**，mapped 中开启缓存约 **0.85%**。这是配对比率的结果，不是把表中两个独立中位数直接相除；不能据此声称对其他尺寸、机器或参考项目有相同比例的收益。

所有缓存配置每次命中 42 次、加载 246 次、峰值保留 6 个块、计账 5,687,678,976 字节，压力回收次数为 0。无缓存时加载 288 个块；含输入/输出 head，分别请求 262/304 次 RAM 放置。这里的计数是放置请求及缓存统计，不是完整分配器驻留证明。所有 16 次整卡显存采样峰值在 2284–2391 MiB 之间，包含桌面等其他进程；没有从该数字推导原生程序独占显存。

mapped 两种配置都出现进程组内存上限事件。无缓存的三次 max 事件为 53353、58453、14067；有缓存为 347539、367568、325766。有缓存的观测峰值最多短暂超过配置上限 188416 字节，OOM/OOM-kill 仍为 0。stdio 两种配置的 max 事件均为 0。文件缓存属于进程组计费但不等于进程 RSS，不能把这两类峰值相加。原生 VmSwap 样本全部为 0；这不证明整个主机从未使用交换空间。

## 决定与限制

RAM 权重缓存继续默认关闭。当前 mapped 模式下，为不足 1% 的配对时间变化保留数 GiB 缓存，收益不足以支持默认启用。mapped 本身有值得继续验证的时间收益，但已观察到文件页限额压力，本轮只有一个 512×512 输入和三次配对，仍保持显式选择；stdio 默认不变。

自动 GPU/RAM 权重放置本来就默认开启；本轮为了控制变量，全部显式使用 RAM。因此这些结果不增加真实显存耗尽、GPU 中间数据卸载或 OOM 恢复证据。结果也没有增加中间张量或官方质量样本，不能替代已有数值失败、正式质量集或与参考项目的 S/M 配对验证。
