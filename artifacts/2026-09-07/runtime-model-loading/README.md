# 运行时加载选择与真实 RAM 压力回收

2026-09-07，新增 `--model-loading default|stdio|mapped`，同一个可执行文件可选择普通读取或 ncnn 映射加载。保留原构建默认值，映射与有界 RAM 缓存仍默认关闭，GPU/RAM 权重放置仍默认 auto。真实 512×512、8 步生成完成，25 个张量、4,981,760 个有限元素与 PNG 逐字节保持原基线结果；但本次映射和 6 GiB 缓存组合的**缓存命中为 0**，没有通过预先冻结的最低命中要求。

## 实现与检查

- 运行请求末尾新增 `model_loading`，结果末尾新增 `mapped_model_loading_requested`，保留旧位置初始化的源码兼容性和不依赖 ncnn 的公共头文件。CLI、API、trace 都明确报告请求的加载策略；ncnn 映射打开失败可以回退文件读取，因此这个字段不冒充实际映射成功数量。
- `model_loading.h` 只负责选择策略，`pipeline.cpp` 把该策略传入文本编码、DiT、VAE 和可用的图生图 encoder。独立 PE 保持既有配置。`default` 遵循原 CMake 开关（默认 OFF），显式 stdio/mapped 可以覆盖它，不改变推理数学或精度。
- 固定 ncnn 的每个 Net 拥有自己的映射。权重会话保留 Net，GPU 命令结束后才允许回收；映射在 Net 析构时关闭。仅调用上游 `Net::clear()` 不关闭这个映射，缓存回收实际使用的是 Net 析构。
- CPU 真实 GEMM 覆盖两种文件存储格式（FP32/BF16）、两种构建默认值的选择逻辑、三个运行参数、重复提取、实际 Linux 映射观察和析构后的释放；缺文件必须失败。Vulkan 真实 GEMM 同时覆盖 stdio/mapped × FP32/BF16 文件，计算仍为 FP32，均返回精确结果，跨三轮缓存命中 4 次、加载 5 次。
- 最终有效的 10 项 Vulkan 构建检查和 6 项 CPU 构建检查全部通过，无跳过，包含 CLI、请求、公有接口和两个安装后 C++ 消费者。首次构建在自动更新 Makefile 后未识别同一次调用中的新目标，显式配置后修正。一次新测试错误地要求 clear 立即关闭映射，核对固定上游后纠正为实际析构边界，只复跑该失败测试。所有原始失败日志继续保留，不记为产品内存泄漏或出图失败。

## 完整模型执行

相同原生 15-token Vector 文本、source32/64 DiT 文本槽、保存初始 latent、512×512、8 步 Vulkan FP32、CPU direct VAE。模型只读，源目录隐藏，网络禁用。运行前后核对 390 个源码、二进制、输入与基线绑定；完整命令见 `plan.json`。本次固定二进制 SHA256：`8383542cee9be25b8441345e9db8c60967b72574b22833416471d7dd2c0b64d2`。

在前次 `--dit-weights auto --gpu-reserve-mib 8192 --dit-cache-mib 6144 --ram-reserve-mib 3072` 上仅增加 `--model-loading mapped`。8192 MiB 显存余量用于主动覆盖 RAM 分支，不是默认值或实际占满显存；6 GiB 缓存、3 GiB 余量和 16 GiB cgroup 都是本次可配置实验参数，不是模型硬件门槛。

组合运行触发了真实 cgroup 内存压力，空闲权重缓存被回收后继续流式计算，完整生成仍结束且输出不变。本次使用的合计内存和映射观察不能把所有新增内存精确归因到各类分配。缓存始终没有获得跨步骤命中，不能把这次运行称为 RAM 缓存加速；时间也不能与历史单次运行直接形成性能优势结论。

## 保留失败与适用范围

原冻结检查器要求至少一次缓存命中，实际返回 1；完整失败日志是 `frozen-comparison.log`。观察到内存压力后另写 `review.py` 做分项复核，记录数值一致、缓存预算有效、真实只读映射成立，但原最低命中要求仍为 false，`all_checks_pass=false`。这份补充分析没有替换原检查器或放宽要求。

这次提供了运行时加载控制和真实压力下回收并继续生成的证据，**没有关闭 O2、正式速度/内存比较或整体超过参考项目的目标**。默认不叠加这两个可选优化；文件缓存与权重缓存的相互影响、重复配对速度、其他尺寸和平台仍待验证。激活搬移、异步分配失败恢复与跨平台 RAM 余量读取也未因此实现。全部任务已经结束；没有推送或发布。
