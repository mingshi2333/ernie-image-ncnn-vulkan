# 运行时尺寸实图与安装版 SDK，2026-09-07

本轮查清新的 64×64 灰图、修复静态 SDK 的依赖导出，并验证安装版在实用分辨率下的完整出图。所有数值容差沿用此前由助手选择的开发诊断值，不代表官方标准或广泛感知质量。历史失败保留。

## 64×64：官方参考也生成灰色纹理

官方完整参考复用原生端已保存的初始噪声、提示词、15 个实际 token、32-token 文本来源、64 个 DiT 文本槽和 8 步调度。根任务独立用 FP64 比较全部 25 个张量、320768 个元素，25/25 通过原 FP32 容差。PNG 平均绝对差为 0.05029296875/255，最大差为 2/255；两端 PNG 均与各自解码张量的量化结果逐像素一致。

实际查看两张图，都是灰色细纹，没有清楚呈现红苹果。这个案例中原生结果与官方模型表现一致，不能把灰图归因于动态尺寸移植或内存不足；数值一致也不代表提示词效果合格。复用了上一轮原生结果，没有重复运行原生 64×64。

官方执行完成，用时 238.029 秒，进程组 memory.current 采样峰值 14868844544 字节，主机可用内存最低 14143496192 字节，整卡显存采样峰值 2610 MiB，max/OOM/OOM-kill 事件均为 0。memory.current 包含文件缓存，不是进程 RSS。CPU2、轨迹记录、反复加载权重及并行的受限编译使该计时不适合作为正式性能结论。

原始 32-token 便携包没有官方权重来源散列，因此第一次参考执行在模型运行前正确拒绝。新增的显式来源补充会认证两个完整源 manifest，要求全部 71 个非图运行文件身份一致，才采用 64-token 来源中已有的官方权重散列。原文本桶和配置不变，fixture 同时记录原配置、目标配置和两个来源身份。7 项实际前置检查通过，改动源/补充来源 manifest、越界尺寸等均在模型执行前拒绝。完整参考通过整个 fixture 的固定散列注册。

原始结果位于 `outputs/runtime-buckets64-v1`、`outputs/runtime64-official-v1` 和 `outputs/runtime64-official-v2`；本目录的 `runtime64/` 与 `runtime64-missing-provenance/` 保存选定日志、配置、来源绑定和独立比较。大张量、图像和模型不进入 Git。

## 512×512 官方参考与 CUDA 缓存

第一次 CUDA 参考在首步后触及原 6144 MiB 整卡保护线，采样达到 6155 MiB，被监督程序终止；没有 OOM。参考脚本现在每块结束后释放闲置 CUDA 分配缓存，不改变张量、权重、步数或运算。六个输入/条件文件、首步预测和 Euler 输出共 8 个文件，与原尝试逐字节相同。

新运行完成全部 8 步及 CPU VAE，实际画出了木桌上的红苹果。用时 235.771 秒，整卡显存采样峰值 2975 MiB，进程组峰值 10460798976 字节，主机可用内存最低 15336148992 字节，max/OOM/OOM-kill 事件均为 0。代表性块结束时，CUDA 保留内存从 1228931072 降至 41943040 字节，而活跃张量占用为 32784384 字节。这些是分配器采样，不是两次完整运行的峰值性能比较。

原尝试在 `runtime512-cache-retained/`，完整参考及首步精确比较在 `runtime512-official/`。两者使用完全相同的初始 FP32 文件，SHA256 为 `1c89a002f18b3162b5a43100dc6f50bdd247dd0af8d1944ec87705153819d453`。官方 DiT 使用 CUDA FP32、禁用 TF32；文本、heads、Euler 和 VAE 使用 CPU。
