# ERNIE 移植工作总览与其他项目复用说明

这份文档记录本项目做过的实现、验证、优化和交付工作，并说明如何把这些经验用到其他原生 AI 项目。适用范围是将官方 Python/PyTorch 模型移植到 C++、ncnn、Vulkan 等运行环境；不同模型需要重新核实数学定义、硬件预算和验收要求。

状态日期：2026-09-08。实现与文档基线为 `1c4ed74`；三平台最终 CI 对应源码 `3a04811`。完整模型和性能数据属于各自报告中的冻结版本，不表示每个后续提交都重新跑过大模型。逐条转换命令见 [ncnn 移植教程草稿](NCNN-DISCUSSION-DRAFT.md)，日常入口见 [README](../README.md)。

**1. 从技术评估到完整原生应用**

先检查官方模型、ncnn 的实际能力和已有移植，再确定组件边界与实现路线。以 ERNIE-Image-Turbo 的 batch=1、8 步、CFG=1 为首个目标，建立独立仓库，分阶段完成真实权重执行，最后接通原生分词、文本编码、去噪、VAE 和图像输出。可选提示词增强器也有原生实现。

最终运行程序不依赖 Python/PyTorch。Python 留在模型下载、转换、打包和官方对照工具中；Rust tokenizer 通过静态库与 C ABI 接入，运行时不需要 Cargo。项目包含 CLI、可安装的 C++ SDK、模型包校验、离线执行记录、跨平台构建和小型测试。

参考了 zimage-ncnn-vulkan、futz12 的 ERNIE 移植和其他原生推理项目的组织方式。已有[参考项目对照](FUTZ12-COMPARISON.md)，但没有完成同硬件、同模型配置的全面性能与质量比较，不能据此宣称全面超过参考项目。

复用时先选一个明确的模型变体和完整用户场景。第一阶段应能从用户输入得到最终输出，再按实际瓶颈扩展功能。模型的“所有变体、所有精度、所有设备”不适合作为第一阶段默认要求。

**2. 锁定来源，让转换与验证可以追溯**

[sources.lock.json](../sources.lock.json)记录官方代码、模型权重、diffusers、transformers、ncnn、pnnx 和 tokenizer 的版本或摘要。运行时 ncnn 与转换器 pnnx 分别记录，避免把“本地某个修改版支持”当成上游已经支持。当前运行时 ncnn 锁定在 `6a1bf000f363714839a36793addc8c879d3d899e`。

转换产物保存图、权重、配置、来源和完整校验信息；长实验另行固定输入、可执行文件、源码清单和命令。权重、构建目录、大张量与生成图片留在本地，小型报告、摘要、日志和失败记录进入 `artifacts/`。执行过程中不会用一个新编译的同名二进制替换已冻结的实验对象。

其他项目可以复用锁版本、记输入、固定二进制和保存失败的做法。ERNIE 的提交号、文件摘要、模型包内容、环境版本和机器参数需要重新生成，不能照搬为新项目事实。新增代码、依赖和模型权重也应分别记录许可。

**3. 按组件转换，逐项核实模型数学**

转换顺序从一个真实 DiT block 开始，逐步扩展到全部 36 个 block、输入输出头、调度器、文本编码和 VAE。每个组件都先用相同输入对照官方，再接到整条流水线。导出成功、图结构合法、真实权重执行、完整生成是四种不同证据。

本项目核实并保留了这些 ERNIE 专有细节：

| 组件 | 实际处理 | 迁移到其他模型时需要重查什么 |
|---|---|---|
| 图像文本编码器 | 配置实际分派到 MistralModel；取前 25 层的 `hidden_states[-2]`，不接最终 norm | 实际模型类、所需隐藏层、mask、位置编码与输出定义 |
| 提示词增强器 PE | 独立的 26 层 Ministral3，带最终 norm、tied LM head、自己的 tokenizer 与聊天模板 | 它是否与主文本编码器共享数学和权重，不能只看模型名称 |
| DiT | 图像与文本联合注意力、三轴 RoPE `[32,48,48]`、shared AdaLN、erf GELU、非仿射最终 LayerNorm | RoPE 布局、注意力掩码、激活函数公式、调制与归一化顺序 |
| latent | 逻辑 128 通道打包布局，按模型统计量反归一化，再还原成 VAE 的 32 通道布局 | 通道排列、空间打包、均值方差、缩放和输出范围 |
| 调度器 | FP32 master latent；按官方 Turbo sigma 序列执行 8 步 Euler 更新 | 时间步定义、CFG、速度/噪声预测含义、浮点运算顺序 |
| VAE | 组件转换与受限空间图特化，配独立目标尺寸官方对照 | reshape 的语义、分辨率假设、归一化和像素量化 |

高分辨率 VAE 的整图 pnnx 转换曾出现持续增长的主机内存占用，已停止并保留失败。后续只对完整摘要认证的 flatten/unflatten 字段做受限特化，并重新执行目标尺寸官方对照。这不构成任意模型图都可以直接修改尺寸的证据。

公式、张量形状和对应实现见 [CODE-STRUCTURE.md](CODE-STRUCTURE.md)。可复用的是核实方法和组件边界，表中的层数、RoPE 分区、通道数、调度公式属于 ERNIE。

**4. 把代码按职责组织，并让 CLI 与 SDK 共用实现**

当前结构保持较浅的层级：

```text
include/ernie/  公共 C++ 类型与生成接口
cli/           参数、UTF-8 输入、图片编码、用户报告
src/           阶段编排、模型组件、形状与内存策略、自定义算子
tokenizer/     Rust 分词器与 C ABI
cmake/         依赖、构建、安装与 SDK 导出
tools/         下载、转换、打包、官方参考与测量
probes/        能单独运行的小型原生诊断程序
tests/         算子、接口、模型包、安装与小型网络检查
docs/          使用、架构、教程与限制
artifacts/     带来源的测量、日志和失败记录
third_party/   固定版本依赖
```

公共接口 [pipeline.h](../include/ernie/pipeline.h)只暴露标准库类型、生成请求、RGB 结果和进度回调，不让使用 SDK 的项目依赖 ncnn 或 PNG 头文件。CLI 和外部 C++ 用户都调用同一个 `ernie::generate`，图片文件编码属于 CLI。

[pipeline.cpp](../src/pipeline.cpp)管理阶段顺序与资源释放；文本、PE、DiT、VAE 各自管理模型数学。模型包与校验、运行尺寸、权重放置、主机缓存分别有独立组件。根 CMake 将依赖、运行库、CLI、探针和测试交给各目录，安装包能被外部 C++ 工程使用。当前生成调用按串行使用设计，没有据此声明并发多会话服务能力。

复用时保持“公共 API、用户入口、阶段编排、模型计算、资源管理、离线工具”这几个边界即可。新模型不需要为了仿照目录而提前建立插件系统、多模型注册中心或通用调度框架。

**5. 修复精度问题，并保存没有成功的尝试**

真实文本条件使 DiT 残差超过 FP16 最大有限值 65504，因此保留 FP32 residual 路径与归一化中间计算，再回到模型存储精度。没有通过裁剪残差掩盖溢出。Euler master latent 保持 FP32，每步检查有限值；Vulkan 正常检查只下载 128 个状态浮点数，完整 trace 是另一种执行模式。

还实现了 ERNIE 所需的 erf GELU、RoPE 和归一化处理。FP32 注意力的 softmax 分母与 P@V 采用补偿累加；CPU VAE 的均值与中心化方差使用 FP64 reduction，其他激活与仿射计算仍是 FP32。VAE 默认直接卷积，以控制已观察到的工作区压力；归约精度问题则由上述数值处理改善。

单算子变好不一定使整模型更接近官方。例如 CPU 文本 RMSNorm 的 FP64 候选在第一层有局部改善，但没有改善完整文本编码，因而没有推广。BF16 的部分完整模型结果仍明显偏离，保持实验状态。

复用时按误差来源选择需要更高精度的位置，并检查整条生成链。不要预设全部 FP16 安全，也不要预设全部改成 FP64 就更合适。

**6. 内存优化分开处理权重、缓存和激活**

已实现的机制如下；它们解决的内存对象不同。

| 机制 | 当前行为 | 适用边界 |
|---|---|---|
| 阶段释放与分块加载 | PE、文本、DiT、VAE 按阶段释放；DiT 按 block 载入 | 降低同时驻留的权重规模 |
| GPU/RAM 权重选择 | 组件加载前查询实际 compute heap 的预算减用量，加上权重估算和保留空间，选择 device 或 host；默认 auto | RAM 权重仍可供 Vulkan 运算；不是执行失败后的重试 |
| 有界 RAM 权重缓存 | 可选缓存已准备的 block，容量默认 0；活跃条目受 lease 保护，压力下淘汰空闲条目 | 减少重复准备权重，代价是额外 RAM |
| 主机可用内存判断 | Linux 考虑主机与 cgroup 祖先限制；Windows 查询物理、commit 和地址空间余量；无法可靠估算时保守处理 | Job/Wine、macOS 等未知范围不据此假定可无限缓存 |
| 映射权重文件 | stdio 与 mapped 是独立加载选项；映射生命周期跟随模型或缓存对象 | 默认 stdio，映射可能增加文件缓存与 cgroup 占用 |
| 注意力 query 分块 | FP32 路径每次最多 128 个 query，保留完整 K/V | 降低单个注意力分数缓冲区，增加提交与同步次数 |
| compact reader 候选 | 修正固定 ncnn FP16/BF16 读取临时 vector 的元素数；只编译经过摘要认证的派生副本 | 默认关闭，已验证解码与一个完整生成样例，不代表普遍提速 |

例如 4160 token、32 head 的一个 FP32 分数缓冲区，从约 2.063 GiB 降至 65 MiB。这只是该缓冲区大小，不是进程或显卡总峰值。compact reader 的小型测试中，同一 8,388,612 字节载荷对应的临时存储从 16,777,224 减至 8,388,612 字节；也不能写成“整个程序内存减半”。

自动 RAM 选择已用人为增大的保留空间触发，并完成与基线一致的 512 图像。这个测试证明加载前的策略分支能工作，没有制造真实显存耗尽。**中间激活卸载、已失败 Vulkan 分配或命令的自动恢复、透明重试尚未实现。** 权重预算估算也不保证后续所有工作区都分配成功。

复用时先测清是权重、激活、临时工作区、主机文件缓存还是其他进程占用，再选相应机制。监督实验的 6144 MiB 等限制是当时的保护配置，不是本模型或其他模型的最低硬件要求。

**7. 正确使用 ncnn KV cache，避免缓存对象混淆**

原生 PE 已接入 ncnn 的自回归缓存。每个会话有独立 cache allocator；CPU 提取使用 `type=1`，缓存按不透明 handle 消费并替换，在 allocator 销毁前释放。不把浅复制 handle 当成独立会话快照。已有真实 26 层、315 个生成 token 到 EOS 的 greedy 对照：token ID、文本完全一致，并通过对应 logit 检查。

默认 PE 仍逐 token 预填充。内部新增 1..32 token 的分块候选，在真实 block0 的 17 token 样例中通过对照；没有完成完整 26 层的候选验证、速度测量或默认切换。

这里有三种缓存：PE 的历史 K/V、不可变权重的 RAM 缓存、Vulkan 编译管线缓存。它们不能相互替代。DiT 每个去噪步的输入会变化，联合注意力中的文本状态也继续变化，因此不能把 PE 的 KV cache 跨步搬到 DiT 并声称是精确优化。

对其他模型应重新检查 ncnn 固定版本的缓存接口、数据形状、所有权和位置编码。新版 ncnn 提供能力，不等于项目自动获得正确的模型接入和性能收益。

**8. 处理尺寸、文本长度和可搬移模型包**

文本图分别导出 32、64、2048 的独立来源，实际分词后选择可用的最小来源。实际 token 数、文本来源长度、DiT 文本槽数是三个不同值，例如 source32 仍保留 64 个 DiT 槽，不能用一个参数混代。

ShapePlan 与认证后的图变换共同生成内存中的运行图，可复用相同权重。实验范围为每轴 16..2048、16 的倍数、面积不超过 2,097,152。2496 次图实例化检查覆盖了三个文本来源与 13 个几何点的组合，但只有部分尺寸执行过完整模型，合法图不等于全部尺寸均已出图验收。

模型包同时检查 schema、配置、每个运行文件的大小和 SHA-256，拒绝缺失、损坏、来源不符和不允许的路径。一个固定完整包包含 136 个运行文件、约 21.67 GiB；这属于该包，不能作为所有模型包大小。下载工具有完整性检查、临时文件与完成后替换，保留既有有效输出，并测试软链接祖先等错误路径。用户需准备本项目格式的包，不能直接把原始 safetensors 当成运行包。

Linux 已完成源码隐藏、网络禁用、含中文与空格模型路径下的安装版完整执行。SDK 也验证搬移后由外部 C++ 工程消费，避免暗中引用原源码或构建目录。相关记录见 [离线完整生成](../artifacts/2026-09-06/offline-linux-generation/README.md)与[共享运行包、SDK](../artifacts/2026-09-07/runtime-images-and-sdk/README.md)。

**9. 完善日常使用，扩展到图生图和 C++ 接入**

CLI 增加常用帮助、完整帮助、无参数入口、UTF-8 提示词文件、进度和 JSON 报告。参数错误、精度冲突、输出已存在等情况尽可能在大模型加载前说明。显式选择 CPU 且未指定精度时默认 FP32；Vulkan CLI 默认 FP16，README 的首张图命令明确选择 FP32。

Windows 系统 UTF-16 边界与程序内部 UTF-8 分开处理，文件路径、参数和报告均有实际检查。输出支持 PNG/JPEG/BMP/TGA；公共 API 直接返回 RGB，不强迫其他应用使用相同图片编码器。提供模型预检、设备诊断、CMake 安装、SDK 消费示例和平台构建说明。

图生图增加编码器、strength 对应的初始化与去噪流程。固定 1024 样例的 strength=0 重建与 strength=0.5 已通过各自完整边界检查；strength=1 虽然完成 8 步、PNG 最大通道差 2，但仍只有 24/29 张量通过。它属于已实现但尚有数值未通过项的功能，不能从两个通过样例推定全部 strength 和图片质量。

**10. 用相同输入分层验证，并公开误差**

验证从 tokenizer ID、组件同输入、整条自由运行轨迹，延伸到解码浮点值和最终 PNG。保存实际初始 FP32 噪声，不用跨框架相同整数 seed 代替同一噪声；C++ 与 PyTorch 的随机序列未必相同。官方参考也锁版本和精度，当前 FP32 对照不能冒充官方默认 BF16 的逐位对照。

指标分开报告 shape、dtype、有限值、NRMSE、最大绝对差，以及 PNG 的平均和最大通道差。项目现有张量/像素门槛是此前为诊断定义的，并非 ERNIE、ncnn 或参考项目的官方标准，也不是经过感知质量校准的评分。新项目应根据用途建立自己的判据；不能通过放宽旧门槛把已知失败改成通过。

**11. 用配对实验评估优化，避免把诊断时间写成速度结论**

完成了同机、同模型、同精度、同输入的 stdio/mapped 与缓存开关四配置实验：每配置一次预热、三次正式测量，共 16 次。全部 PNG 逐位相同，OOM/OOM-kill 为 0。冻结源码 `b6b80d3`、二进制 `ff2f934f`，512×512、显式 RAM 权重、2 CPU 线程、trace 关闭。

| 配置 | 三次耗时中位数 | 原生进程峰值 RSS 中位数 |
|---|---:|---:|
| stdio，缓存 0 | 500.252 s | 1.824 GiB |
| stdio，缓存 6144 MiB | 465.762 s | 6.276 GiB |
| mapped，缓存 0 | 395.931 s | 1.947 GiB |
| mapped，缓存 6144 MiB | 393.330 s | 9.102 GiB |

按三次配对耗时降幅的中位数，mapped 无缓存比 stdio 无缓存降低 20.85%；mapped 再加缓存降低 0.85%。这些百分比不是上表两个中位数的直接比值。页缓存和后台负载未完全控制；mapped 模式还触及包含文件缓存的 16 GiB cgroup 限制，因此不能声称它普遍降低整机内存。映射和 RAM 缓存保持可选。完整记录见[配对实验](../artifacts/2026-09-07/memory-grid512/README.md)。

compact reader 已通过一个独立完整生成的 25 张量和 PNG 逐位回归，但对应耗时含 trace，不能与该表直接比较。另一个 reader 配对速度实验只完成准备，按用户要求延期，没有运行。推测性的预取与 head 缓存也没有继续扩展。

其他项目应先测热点，固定参数并保留正确性对照，再做最小优化。CPU RSS、cgroup（含文件缓存）、整卡占用、进程 GPU 分配要分别记录；父阶段和嵌套子阶段耗时不能重复相加。完整 GPU 作业串行执行，代码阅读或独立文档可以并行；已有并发大模型分配失败，不能据此推定单任务硬件容量不足。

**12. 完成原生三平台 CI，修复实际平台差异**

[build.yml](../.github/workflows/build.yml)覆盖 Linux CPU、Linux 软件 Vulkan、Windows 原生 MSVC、macOS 原生 Apple Clang/MoltenVK；compact reader 的 OFF/ON 各对应一个 Linux CPU 作业。使用固定 Actions 引用、递归依赖检出、Rust 锁文件、有限构建并行度、超时和手动平台选择，失败时保存日志、CMake 配置与 CTest XML。每次提交的 CI 不下载完整大模型。

**14. 给其他项目使用的执行顺序**

1. **确定交付目标。** 写清模型变体、用户输入输出、首批硬件、离线要求和一组有代表性的样例。明确功能、数值接近、画质/任务质量、性能分别用什么判断。
2. **建立可信基线。** 锁定官方代码、权重、框架与转换器；保存真实输入和官方组件/最终输出。先验证官方基线本身能复现。
3. **画出组件与张量关系。** 标明 tokenizer、编码器、主网络、状态更新、解码器，以及必要的 shape、mask、位置编码、归一化和精度。
4. **移植一个真实组件。** 做同输入对照，再扩到完整主网络和原生输入输出链。用小探针定位转换、算子、数据布局和精度问题。
5. **建立简洁运行结构。** 公共 API 与 CLI 共用流水线；阶段、模型数学、文件包和资源生命周期分工明确。只有实际需求出现后才抽象公共机制。
6. **先完成可靠的日常使用。** 提供首个可复制命令、参数预检、Unicode 路径、进度、报告、校验模型包、安装与离线搬移验证。
7. **按测量优化。** 优先阶段释放、分块加载和有限缓存；确认内存对象后再决定 attention 分块、映射或其他策略。改动必须说明默认值、正确性证据、收益及代价。
8. **分层验证与留证。** 小测试覆盖日常改动；真实组件和少量完整样例验证模型改动；固定工作负载测性能。保存失败、跳过、版本和原始指标，不把合成测试当完整模型。
9. **做目标平台原生 CI。** 检查本地编译、运行、驱动能力、安装搬移和外部消费者。未具备的设备能力明确跳过；完整大模型由独立实机验证承担。
10. **交付可以查证的说明。** README 写第一次使用、架构、实测误差和限制；复杂细节放教程和报告。已有结果足够支撑当前功能时停止重复验证，后续工作由实际问题驱动。

可直接交给另一项目的开发者或 AI 的任务说明：

> 参考这份 ERNIE 原生移植记录，为当前模型建立从官方实现到本地应用的完整路径。先核实当前仓库和模型，不复制 ERNIE 的层数、尺寸、版本号、硬件限制或数值门槛。按“来源与基线、组件同输入对齐、完整原生流水线、清晰 API/CLI、模型包与离线交付、按测量优化、分层验证、原生平台 CI、文档”推进。每项改动说明解决的问题、证据和剩余限制。把 PE KV、权重缓存与激活管理分开；把构建、小型算子、完整执行、数值、任务质量和性能分别报告。已有通过实验只在相关实现变化或仍有明确疑问时重跑，不提前建设没有需求的通用框架。最后交付可运行代码、实际测试记录、首次使用说明、架构图或源码导航、误差与已知问题。
